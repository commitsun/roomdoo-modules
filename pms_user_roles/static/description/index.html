PMS User Roles

Builds the management of PMS users on top of the user roles of base_user_role:

  • A catalog of roles for the usual PMS profiles: base internal user, reception, revenue, administrative, manager and call center.
  • Profile managers: users who assign the roles flagged as assignable to internal users without being access rights administrators.
  • An All properties option on roles, for teams that work across every property (support, for instance): holders get every active property and its company, and lose them again when they no longer hold the role.
  • Safety nets around the role recompute of base_user_role:
    • a user whose roles grant no user type stays an internal user instead of silently becoming a share user without groups;
    • a role line created on its own (from the role assignments menu, data files or RPC) is applied right away;
    • a daily job reports users that hold the group of a role without a role line, which the recompute never updates.

Usage

Roles

In Settings > Users & Companies > Roles, access rights administrators configure the roles. Two options are added:

  • Assignable: profile managers may assign the role. A role that grants Settings, Access Rights or Profile manager cannot be assignable.
  • All properties: holders get every active property and the companies of those properties. The role must grant Multi Companies. What the option adds is removed when the user no longer holds any role with it; properties and companies the user had before are kept.

None of the catalog roles is assignable out of the box.

Profile managers

Give the Profile manager group to the people in charge of user profiles. They get a Roles > Role assignments menu where they add, change and remove role lines, with these limits:

  • only roles flagged as assignable;
  • only active internal users who are not administrators nor profile managers, and never themselves;
  • a user whose permissions are still set by hand (no role yet) cannot be given a role that would take permissions away: an access rights administrator migrates those users.

Each operation is logged with the profile manager, the role and the user.

Assigning roles replaces groups

A user with at least one role line gets exactly the groups of their enabled roles: groups set by hand are removed on the next recompute. Ticking the group of a role in the Access Rights tab does not assign the role; roles are assigned through role lines only.

Known issues / Roadmap

  • The catalog is a stable set of names, not a mapping of today’s permissions. pms defines three groups (user, manager and call center), so the reception, revenue and administrative roles are identical inside the PMS: they only differ by the groups of other applications that each installation adds. Telling them apart needs new groups and access rights in pms.
  • Assigning a catalog role to an existing user replaces all their groups. A PMS manager given PMS / Reception loses the manager rights. Review the groups of each user before moving them to roles.
  • res.users.pms_api_user_role, used by the front end, is not derived from the roles yet.
  • With base_user_role_company the recompute runs on every login and session information request; the safety nets are no-ops for users that need no change, but this combination is not covered by tests.
